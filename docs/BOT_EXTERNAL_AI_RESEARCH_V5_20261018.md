# 小国戦線III｜外部RTSゲームAI研究レビュー V5（2026-10-18）

## 本文の位置づけ

現行BOTを `botExpertAction` の固定優先ルールだけから、観測した局面をもとに合法な代替手を比較するBOTへ発展させるための**一次論文・実装資料の調査結果**。これは調査・設計文書であり、今回は公開BOTの実装やゲームの対戦ルールを変更しない。研究手法をそのままコピーしても本作の勝率改善は保証されない。

2026-10-18現在の研究版（develop）：
- `docs/BOT_ACTION_ROLLOUT_SEARCH_V1_20261018.md`：実際の30Hz `tick` で手札・合法な召喚位置を20秒分岐比較した。
- `docs/BOT_ROLLOUT_RESPONSE_HORIZON_V2_20261018.md`：敵の反撃仮説と8/20/32秒予測で選択が変わることを測定。
- `docs/BOT_TWO_STEP_ROLLOUT_V3_20261018.md`：6秒後に二手目を再探索。
- `docs/BOT_BOUNDED_ROLLOUT_V4_20261018.md`：二手目だけ絞ると24/24固定局面で初手一致。一手目も一律6候補に削ると5/24不一致。どちらも実戦勝率の証明ではない。Chrome CIでも一探索に数百ms級の局面があり、学校iPadでそのまま動かすのは危険。
- 既存の `captureSpendGate` は学習では勝っても独立holdoutで負け越した。既知seedを調整の根拠として繰り返し使わない。

## 調べた資料と正確な示唆

### 1. Portfolio Greedy Search (PGS) — Churchill & Buro (2013)
https://doi.org/10.1109/CIG.2013.6633643
https://ieeexplore.ieee.org/abstract/document/6633643

StarCraft戦闘で、各ユニットの膨大な行動を、強い既知の戦闘用scriptの選択へ抽象化。SparCraftという高速な抽象戦闘モデルと組み合わせ、50 vs 50規模を40ms制約下で探索した研究。

本作への提案：**従来BOTの戦術は廃棄せず、意味の異なる「候補提案者」に分解して探索へ流す**。例：城防衛／飛行迎撃／大型迎撃／砦占領・再奪取／城ダメージレース／資源温存／基本BOTそのまま。合法手のみ採用し、長所の異なる役割が少なくとも各1案は候補に残れるようにする。

注意：PGSを丸ごと実装する必要はない。現行ゲームは「ユニット個別操作」でなく「手札から召喚・自動戦闘」で行動粒度が異なる。

### 2. Action Abstractions for CMAB Tree Search — Moraes et al. (2018)
https://doi.org/10.1609/aiide.v14i1.13018
https://ojs.aaai.org/index.php/AIIDE/article/view/13018

μRTSの大きな行動空間を通常・非対称な行動抽象化により縮小。マップの大きなケースで特定アルゴリズムとの対戦優位を報告。

本作への提案：**候補を高スコア順に単純6件へ削ってはいけない。** 実測V4で、大型対策のguardian、攻城tank、射手archerが候補から消えた。敵の規模・クラス・城/砦位置の危険性に応じ、重要役割ごとに保護枠を置く「role coverage」。ただし今の固定24場面にだけ合わせて保護枠を調整すると再び過学習する。今後初めて評価する別の局面群を試験用に準備する。

### 3. Game-Tree Search over High-Level Game States — Uriarte & Ontañón (2014)
https://doi.org/10.1609/aiide.v10i1.12706
https://ojs.aaai.org/index.php/AIIDE/article/view/12706

全ユニットの連続的挙動をそのまま全分岐で探索する代わりに、戦況を高レベルに抽象化した表現で枝数を削減。StarCraftにおけるalpha-betaやMCTSの結果を報告。

本作への提案：まず **前線・砦・局所脅威・城ダメージ到達時間・資源/手札到達時間** を数十項目に要約し、低コストな候補評価で選択肢を粗く比べる。そのうえで上位と各戦術保護枠、および旧BOTが選んだ一手のみ、本物の30Hzエンジンで検証する。簡易モデルの推定ミスもログに残す。モデルが未校正なら本番へは入れない。

### 4. Rolling Horizon Evolutionary Algorithms for General Video Game Playing — Gaina et al. (2020)
https://arxiv.org/html/2003.12331v2
https://arxiv.org/abs/2003.12331

有限長の行動列を探索し、その先頭を実行したあと再計画する手法。複数ゲームにおける探索深さ・予算・変異等のパラメータが結果を大きく変えること、深さを動的に変える拡張の存在を示す。

本作への提案：今の+6秒の再計画設計と近い。8/20/32秒で最善評価カードが「待機/歩兵/工兵」と変わったため、**脅威到達時間、砦接敵、資源回復・次のカード購入可能時刻**をもとに horizon の候補を定義し、時間窓の効果を独立対戦で検査。深くするだけでは勝率に直結しない。

### 5. Nested-Greedy Search — Moraes et al. (2018)
https://doi.org/10.1609/aiide.v14i1.13017
https://ojs.aaai.org/index.php/AIIDE/article/view/13017

PGSに、全行動を評価できても最善が見つからない場合があることを指摘し、μRTSで別の探索方式を評価した研究。

本作への示唆：**role coverageを入れれば必ず最善になるわけではない。** 早期剪定の危険、探索の手順依存性、評価関数の偏りを検査し、旧BOT案と待機を必ず残す。行動の評価に細かな微差しかないなら無理に置換しない。

### 6. MicroRTS — Ontañón / Farama（研究用RTS）
https://github.com/Farama-Foundation/MicroRTS
https://sites.google.com/site/micrortsaicompetition/microrts

小規模・実行しやすいリアルタイムRTS環境。ハードコードされたbot、各種の木探索、対戦評価がある。**独立対戦・シード・対称条件・異なるプレイスタイル**を揃える評価方法の参考になる。ただし別ゲームなので戦略の勝敗は移植できない。ソースはGPL-3.0であり、ここでの作業は原理・公開論文を参照するのみ。**ゲーム実装コードはコピーしない**。

### 7. Web Workers / requestIdleCallback — MDN
https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API
https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback

Web WorkerはUI/描画のメインスレッドと分けて重い計算を実行できる。ただしDOMアクセス不可、state clone・messageのコスト、ホストとサーバのゲーム状態一致、埋込single-file iPad配布でのロードを考慮する必要あり。`requestIdleCallback` はMDNで限定的な互換性とされるため、学校Safari前提の唯一のタイムスライス機構にしない。Worker導入は十分に小さなsearch-only状態表現ができてから検証し、**オンライン通信へ触る必要を作らない**。

## 小国戦線IIIに最も適合すると考える提案

**ハイブリッド「戦術ポートフォリオ + 二段階評価 + 必要時探索」の順に研究する。**

1. ゲート（まず実戦データの監査）：既存BOTが合法な一手を容易に選べる通常の局面、特に即時防衛・城危機には必ず軽量な既存判定を残す。接戦で異なる戦略が成り立つ局面（砦を捨てる/防衛、城レース、2種以上の有効カード、防御と貯蓄が競合）を、実試合の`runDuel`観測で検出。**その判定の取りこぼしと呼び出し頻度を測り、後から閾値を調整して同じデータで採用しない**。
2. 戦術スクリプトを候補提案者として併用：既存BOT案・待機・飛行迎撃・大型迎撃・城急襲対策・占領役・攻城役・節約プラン。提案候補はすべて**現在実行できる合法な手札・資源・配置の範囲内**。各役割を一枠だけ保護し、意味の重複した候補は座標・役割別で重複除去。
3. 安い戦況モデル（第1段階）：脅威の接敵まで秒数、味方・敵の空地火力、砦の所有と前線距離、自軍城HPと予測相手城損害、次の重要カード支払い猶予をもとに候補をざっくり評価。計算量は計測して上限化し、推定誤差の極端な場面を記録。
4. 本物の30Hz分岐シミュレータ（第2段階）：第1段階からの有望候補、重要役割の保護枠、旧BOT案、待機だけ比較。敵の**非公開手札・将来の行動ラベルを覗かない**。敵反撃は複数の公開合理的シナリオを仮定し、平均と最悪リスクのバランスを確認する。
5. 予算の制御：探索が必要なときだけ実行、繰り返し同じ場面をフル計算しない、終了時刻に達すれば旧BOT案に戻る。オンライン30Hzの計算・描画を阻害してはならない。将来的にWorkerを検討するが先に**思考時間と第95百分位のフレーム遅延**をChromeと実機Safariで測定する。

## 比較実験の順序と安全基準

- 第1段階：今までのV4固定5場面+追加24場面を**回帰テスト専用**として使い、飛行/大型/城危険/複合防衛の合理的候補を失っていないか確認する。
- 第2段階：上記と異なる固定戦況を自動生成し、旧フル探索と比較して「最善と評価された候補を候補生成段階で落としていないか」「短いスコア最善でも城HPが悪化していないか」を記録する。観測したセットを繰り返しチューニング用に流用しない。
- 第3段階：**フル対戦A/B**。同じシード、異なる先手後手、自己対戦および複数スタイルの敵、自然な手札循環、時間切れと城落城で比較。敵の公開資源推定誤差も計測。
- 第4段階：研究セットで改善が十分な場合のみ、まったく別の未使用seedの独立holdoutとiPad Safari負荷・操作遅延・オンライン通信の退行検証へ。
- 実戦勝率/城HPに安定した改善がない場合、**候補の削減・探索の美しさだけを理由に通常BOTへ反映しない**。本番は既存版のまま。

## 優先順位

**第1候補：戦術ポートフォリオの候補欠落率をQAで調査する（将来の実装）**。これは過去V4の「第1手を一律削ってしまい5/24で判断が変わった」という具体的な失敗に直接対応する。

**第2候補：実対戦での探索ゲート発動頻度・漏れの観測**。3番目以降に抽象シミュレータ導入やWorker検証を置き、現行の30Hzゲーム本体や公開mainは触らない。

ここに挙げた手法の移植効果は**未検証の仮説**。研究論文が実証するのは各研究の対象ゲームと実験条件であり、小国戦線IIIでの強さの証拠ではない。
