# 小国戦線III｜探索ゲート V7｜実試合での発動頻度・同期実行負荷（2026-10-18）

## 結論

前回V6までの「戦術ポートフォリオ＋第2手探索」は、固定局面では候補欠落率を改善したが、一度の思考に数百ミリ秒かかることがあり学校iPad Safariのリアルタイム更新には危険だった。

今回は、**探索してよさそうな局面を可視情報から判別し、探索は実行せずに完全試合で動作検証**した。結果として候補は全判断の**2.3%**に減ったが、さらに軽い**8秒×2分岐の実物エンジン負荷でも最大20.3ms**の同期停止が出た。通常ゲームの同期BOTとして統合するにはまだ危険。**本番投入はしない**。

## 実装の所在と保護範囲

- `tests/online-bot-search-gate.inc.js`：実際の30Hzゲーム `botExpertAction` 直前に、QAサーバが**一時的に**監視処理を注入。ソース自体はGitHub上の `online-game.js` を編集していない。
- `tests/online-bot-search-gate.cjs`：6種類の固定盤面で分類動作を確認し、rush/balanced/fortress/banker/self ×seed241/293×戦術側1/2の**20組の完全試合ペア**を通して呼び出しの漏れ・試合結果の不変性を確認。
- `tests/online-bot-gate-branch-cost.cjs`：別の10組の完全試合ペアで、ゲートが選んだ場面に限り1回最大6件／試合の**QA専用短期シミュレーション負荷**を実測。重い探索を本番と同様のメインスレッドで動かす危険を検査。
- `.github/workflows/online-bot-search-gate.yml`、`.github/workflows/online-bot-gate-branch-cost.yml`：Actions実測ログと30日保存のJSON成果物。
- **公開main / 現行BOT / 通信 / HTML / カード能力 / 配布ゲームに一切変更なし**。QA側の実試合観測でも一切新しいカード行動を選ばない。

## ゲートが使う情報

判定対象は自軍の現在の合法手札・資源、敵の**見えている部隊の種類と座標**、自軍部隊、砦の状態、両城の現在HP。敵の隠れた手札・将来の追加召喚・敵の資源の真の値・QA相手スタイルを覗かない。

まず緊急の城防衛、資源不足、使用可能カードが1種類しかない局面、明らかに別戦術と比較する必要がない局面を除外する。探索候補の対象は、砦の防衛／放棄と再奪還の競合、敵味方が砦周辺で接触中、大型投入とテンポ重視のトレードオフ、対空と地上対応の競合、城への攻撃レース等。

同じ局面を連続で重く評価しないよう、**各チーム最低12秒の探索間隔**を要求する。ただしこの数値はまだ探索の実運用で選ばれた最適な閾値ではなく、QAでの暫定値。従来BOTは探索候補か否かに関係なく通常通り同じ手を実行する。

## 完全試合での監視のみの実測

**[Actions #39134446583](https://github.com/8mahi8/shokoku-sensen/actions/runs/39134446583) SUCCESS**。さらに負荷計測用observer修正後の同じ監視テスト **[Actions #39134706158](https://github.com/8mahi8/shokoku-sensen/actions/runs/39134706158) SUCCESS**。

同じseed・敵スタイル・陣営で観測あり／なしのゲーム結果について、勝者、試合時間、城HP、使用したカード、召喚費用、資源、砦所有秒などが一致。**監視してもゲームの結果は変わらなかった**。これはゲートそのものの公平性・副作用のなさの確認であり、通常BOTより強くなったという意味ではない。

| 指標 | 結果 |
|---|---:|
| 完全試合ペア | 20組（同条件での観測有／無、計40シミュレーション） |
| BOTが意思決定した回数 | 1,785回 |
| 探索候補と評価した回数 | 69回（3.87%） |
| 12秒間隔を守った選択 | **41回（2.30%）** |
| クールダウンで追加検索を省略 | 28回 |
| 資源が2未満で候補なし | 1,007回 |
| 合法な代替カードがない | 614回 |
| 戦術上の比較必要性がない | 89回 |
| 城の直近危機（従来BOT優先） | 6回 |

なお「砦が争奪中」という兆候自体は828件観測したが、その多くは「エネルギー不足」「代替カードなし」などの理由で重い探索を呼ばない。正しく「選ぶ余地がない」局面を分離できている可能性があるが、すべてが正しいフィルタだという勝率検証は未実施。

各相手スタイルでの選択数：rush 12、balanced 6、fortress 6、banker 13、self 4。この分布は限定seedの観測であり、敵戦術の分類器や性能保証ではない。

固定分類QA：無害な序盤→不必要、城前敵→即時防衛、争奪中の砦→候補、地上＋空中の同時敵→候補、7コスト大型と占領の比較→候補、資源1.1→探索不可、がそれぞれ期待通り。

## 選ばれた局面での「本物の30Hzシミュレーション処理時間」試験

**[Actions #39134760994](https://github.com/8mahi8/shokoku-sensen/actions/runs/39134760994) SUCCESS**。

追加で10組の完全試合ペアを実施。これらのペアも監視／短期分岐試算ありなしで、同じデッキ・勝敗・城HPなどの対照結果が変わらなかった。

ゲートによる選択は計23回。このうち1組ごと上限6回の記録と試合終盤回避に従い、実際に**20件の短期分岐計算**を測定。内訳は、原則 `wait` と合法な1カード召喚の合計最大2選択肢を、それぞれ実ゲームエンジンで8秒＝240フレーム進めたもの。**合計9,600フレーム**。乱数は本体と独立のseedを使用。ゲーム状態・統計・乱数関数を評価前に戻す。これは最低限の分岐負荷計測であり、20秒／多数候補の本来の探索の計算量を表していない。

| 負荷指標 | 実測 |
|---|---:|
| 2候補×8秒の実物エンジン計算・中央値 | **4.1ms** |
| 90パーセンタイル | 9.2ms |
| 95パーセンタイル | **16.1ms** |
| 最悪ケース | **20.3ms** |
| 短期分岐の実計測数 | 20件 |
| 30Hzシミュレーション実行総数 | 9,600フレーム |

60FPS画面の目安1フレーム16.7msを、軽量な2分岐試験でも超えることがある。学校iPad Safariではメモリ・処理性能・タッチ操作が異なるため、この数値を転用してはいけない。軽量化により頻度が減っても、**1回の大きな同期実行時間がなくなるわけではない**。オンライン対戦・端末UI・30Hz物理への悪影響を避ける必要がある。

## 今回判明した実務的な判断

- **採用（研究のみ）**：戦術的な分岐があり、合法な選択肢が複数、城が直近で危険ではない場合だけ探索候補として記録する、12秒間隔付きの安全側ゲート。
- **不採用（まだ）**：候補となったすべての局面で、従来の20秒・複数反応・二手探索をメインスレッド同期で起動する設計。ゲート率2.3%でも1回あたりのスパイクを許容できない。
- **未実証**：ゲートと本当の探索を結合したBOTの対戦勝率、ゲーム上の強さ、iPad Safariの処理時間、画面カクつき、オンライン通信遅延。

## 次の開発工程

1. **探索の実行を分割・隔離**：Web Worker またはイベントループを塞がない小ステップ処理を比較する。ゲームの描画とは別のところで計算するだけでなく、状態スナップショットが古くなったときは無効化、手札・資源の再合法判定、通信遅延と一致性の確認が必要。既存iPadの単体HTML配布・Google Sites埋込みを破壊しないようQAで検証。
2. **役割ポートフォリオ×短い候補選別**：高リスクな第2手近似によるランキング差があり、軽量版とフル版の候補差が原因とは限らない。初手の保護は維持し、短い予測で安易に勝率を主張しない。
3. **最初の本当のA/B勝率**：探索がリアルタイム予算内で実行できたら、ゲートON/OFF、全体の従来BOT・敵の複数戦術に対し先手後手／同一seed条件で完全な試合を比較し、研究セットと独立holdoutを別にする。**今回の監視で結果不変だったことは勝率改善の証拠ではない。**

現段階では実験コードは `develop` に隔離し、**公開mainには一切触れない**。負荷と正当性が揃ってから昇格を検討する。
