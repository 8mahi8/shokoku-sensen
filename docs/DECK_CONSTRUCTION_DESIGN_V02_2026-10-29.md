## 1. 設計原則

1. **デッキは「採用するカードIDの集合」**。個別カードのHP・攻撃力・AI・アートなどの定義元は既存 `CLASSES/SPELLS/CATALOG`。デッキが性能を上書きしない。
2. **常設歩兵は外枠**。8枚選択枠へ混ぜない。常設歩兵と手札4枚の戦闘UI合計5枠を維持する。
3. **8種類の取捨選択で戦術差**。同じカードを8枠に複数置いて回転を極端に早める構成は初版では認めないことを推奨（重複禁止は未合意）。
4. **戦闘の循環そのものは極力変えない**。残回数・コスト・手札更新・ユニットAIは既存を流用。デッキ構築を口実に単体カードバランスを一斉改造しない。
5. **短時間・少タップ・迷わないiPad操作**。長いドラッグ、入力フォーム、複数の保存画面を必須にしない。
6. **本人と友達の編成は別々**。相手のデッキをUIで事前公開しないことを推奨。ただし現在のFirebaseの部屋読取権限では暗号学的な秘匿は提供できず、「非表示」≠「データが読めない」。

## 2. ルール候補（提案＝未承認）

| 項目 | 推奨仕様 | 理由・保留点 |
| --- | --- | --- |
| 編成 | `infantry`常設＋その他**8種類** | 本人の方向性と一致 |
| 手札 | 同時4枚／常設歩兵は別 | 既存の戦闘操作・UI・テンポを維持 |
| 同ID重複 | **禁止を推奨** | 同名を2枠置いた時の使用回数／個別クールダウン管理が新しい意味を持つため |
| ユニット／スペル | 8枠に両方自由に入る。スペル数の必須／上限は初版なしを推奨 | 極端な編成はプレイヤーの選択にする |
| カードの開放・レベル | 一切なし | 学校の友達に公平、編集も簡単 |
| 使用限度 | `CATALOG[id].limit`を維持。1枚当たりのリセットは試合開始時 | 現行のキャラ性能を壊さない |
| デッキの並び | **編成画面上の順は手札順ではない**。試合開始時に独立シャッフル | 配置戦略と引き運を両立。既存の開幕シャッフルに近い |
| 使い切ったカード | 待機列に戻らず、手札枚数が減ってもよい | 既存`advanceHand`の仕様継続 |
| 編集できる時 | ルーム参加前、ロビーで準備完了前、再戦時 | 準備完了後の勝手な差し替えを防止 |
| ローカル保存 | 使えれば保存。ただし保存不可でも必ず対戦可 | Google Sites埋込Safariで永続ストレージを保証しない |
| BOT | 友達1vs1を先行。オフラインBOTの従来10枚循環は保護 | BOTの固有カードID判断を同時に全面改修しない |

### カード循環の具体例

選択したカード集合 `[A,B,C,D,E,F,G,H]` を開始時にランダム並び `[D,A,F,B,H,C,E,G]` にする。手札 `[D,A,F,B]`／待機列 `[H,C,E,G]`。

- `A`を使用、残回数あり → Aを列の末尾へ、次のHを手札へ。手札 `[D,F,B,H]`、列 `[C,E,G,A]`。
- `D`を使用して残回数0 → Dは列に戻さず、次のCを補充。
- 待機列も枯れたら手札は4枚未満になり得る。**無理な補充や「使い切ったカードの復活」は行わない**。
- 歩兵はこの8枚循環に参加せず、エネルギーがあれば常設枠から使える。
- 単にリスト順を指定して初手を操作できないよう、**試合開始時に一度シャッフル**する。再戦も新しい独立シャッフル。現在の「青赤が同じ最初の4枚の順にならないよう再抽選」仕様は互換性評価対象とする（独立デッキになると同じ8種類を選んでいる場合に限る問題）。

### ゲームバランスで検証する点

- 10→8種類へ減るので、同じカードへの再遭遇が速くなる。**大型・範囲スペルの利用機会が増え、試合が速くなる可能性**がある。断言せずBOT実戦で確認。
- 攻撃／防衛／対空／占領／範囲スペル／平均エネルギーコストを編成画面で簡潔に可視化する。**平均コストには常設歩兵の2を含めない**（8選択カードの平均と明示）。
- 「対空できるキャラが0枚」「占領が歩兵だけ」「高コストに偏る」は**注意表示のみ**の方針を推奨。禁止すると自由度が減る。標準歩兵の占領力1で必ず砦占領手段が残る。
- 具体的な「初心者用・標準デッキ8枚」はテストの感触を見て別途選択。現行10枚からランダムに8枚取って固定することはしない。

## 3. デッキ選択UI（iPad Safari／Google Sites）

**最初のプレイで8回選ぶことを必須にしない**。起動時は仮の標準8枚が選択済み。友達とすぐ遊ぶ時はそのまま「準備完了」でよい。

- ロビー：上部に「現在のデッキ 8/8」、選択した8枚。下部にカード一覧（現在は10種類）、2つの未採用カードは薄い表示と「追加」。
- タップで選択解除／追加。8枚の状態で未採用カードを触った時は「交代する1枚を選択」と表示し、次のタップで1枚入れ替える。ドラッグ不要。誤操作キャンセルあり。
- 新キャラ増加時も一覧は `CATALOG`から動的構築。選択対象は歩兵以外で「編成可能」のメタ情報を持つカードに限定する想定。**現在の固定`DECK_IDS`を新キャラごとに更新し続ける構造は将来の改善対象**。
- カードをタップしたときの交換選択と、長押しで能力詳細を見る操作を明確に区別。初版はタップ／「詳細」ボタンの方が安定する可能性あり。
- 編成が7/8以下なら準備完了不可、理由を即表示。8/8ならボタンが有効。
- 8枚の平均コスト、対空カード数、占領カード数、スペル枚数を簡潔に表示。数値表示が不安になるならタップで折り畳み可能。
- 目標タップ領域は44×44 CSS px以上、横持ちiPadで1画面内に主操作が収まるようにする。小さい画面では一覧領域のみスクロール。キャンバスのゲーム描画は裏で回さない／負荷抑制。
- 「標準に戻す」ボタンは用意。複数の保存枠、名前変更、公開デッキ共有、カードソート／フィルタは初版必須にしない。

## 4. ステートの責務（設計上の分割）

```text
CATALOG ───> eligibleCards ──> local draft deck (editable 8 IDs)
                                  │
                                  └─[ready submit]──> room lobby record
                                                         │
             HOST [round/seat/version/ready/valid] ─────┘
                                   │
                          frozen match decks [blue, red]
                                   │
                           per-team shuffle (8)
                                   │
                S.hand[team] (4) + S.queue[team] (4)
                                   │
                      existing pay/deploy/fire/AI
```

- `DeckCatalog`：既存のカード定義 `CATALOG`を参照し、編成可能なカードIDと表示情報を返す。**新キャラの行動AIとは独立**。
- `DeckRules`：常設ID、選択数8、手札数4、同ID重複可否等のルールを一箇所に宣言。数値とゲームコードが二重にハードコードされないようにする。
- `DeckValidator`：文字列ID×8、重複なし、対象プールに全て存在、歩兵含まない、バージョン妥当性を判断。**見た目だけでなくホスト側も実施**。
- `LobbyDeckState`：編集下書きとは別の「提出済み8枚／準備状態」。準備解除と編集は同一レコード更新で`ready=false`にする。IDやroundの混入を拒否。
- `MatchDeckState`：対戦開始時に確定した青赤の各8枚。試合中不変で、使用上限・手札・待機列は既存`S.left/S.hand/S.queue`に初期化。必要ならホストの`hasCard`はこの集合への所属も検証。
- ゲストのローカル選択UIや`selected`は操作表示のみ。**ゲーム本体とホストが最終判断する**。対戦中のFirebaseに毎フレームデッキ定義を付加しない。
- 保存領域は`LobbyDeckState`でも`MatchDeckState`でもない。任意のローカルプリセットであり、失われてもその試合の確定済みカードには影響しない。

## 5. Firebase／ロビー／開始を壊さない設計

### 現行コードとの齟齬

- 現在`online-net.js`では`players/{host|guest}/ready`と`meta/status`が別ノード。現在の`startMatch()`は`meta`に対するtransactionで`status=playing`にするが、transactionの中では`players/ready`とデッキを同時検証していない。
- **新しいデッキを外付けしてゲストの準備中編集と開始を競合させるのは避ける。** おもての`ready`表示と、開始ゲートの根拠は同じスナップショットから出す必要がある。
- 初版実装案：既存ルーム内の`meta/lobby/{host|guest}`に`{seatId,round,revision,cardIds,ready}`を置き、その`meta`を**開始ロックの単一transaction対象**とする。transaction内で同一round、参加席ID、8枚妥当性、両readyを検証してから`status=playing`と`lockedDecks`を**同じcommit**で確定。
- `players/{seat}`は接続状態の正本として維持し、開始操作の直前に最新の参加席と照合。ロビーの`ready`の正本は`meta/lobby`へ統一する設計を推奨。現在の既存`players/ready`をそのまま独立したゲートとして併存させない。
- その場で再評価されるtransactionと、子ノードの`set`等の混在／取消・再実行はFirebase Emulator Suiteで**実際に競合テスト**する必要がある。これは設計案であり、接続環境での安全性を未検証。
- `lockedDecks`は`{round,host:[8 IDs],guest:[8 IDs],hostSeatId,guestSeatId,version}`のような**ラウンド付き固定スナップショット**。世界の高頻度同期`state`とは別。
- 同期順の必須条件：`meta.status=playing`を見て`game.begin()`が走るより先に、同一transactionで設定済みの`lockedDecks`を読み込めること。未受信／不正なら開始しないで再読込・明示的エラー。勝手な固定10枚へのフォールバックはオンラインでは禁止。
- クライアントの互換性バージョンを引き上げる案（現状`ROOM_VERSION=2`）。古いGoogle Sites版とデッキ構築版が同じルームを使って初期手札の解釈がズレないようにする。**変更は実装時に検討するが学校公開はしない**。
- 対戦前の相手デッキを画面に明示しないのはUI方針。Firebaseに同じ部屋として保存した時点で実際のデータ秘匿にはならないため、秘密デッキをセキュリティ上の保証にはしない。

### ロビー状態遷移

`未参加/編集中 → 8/8完成 → 準備完了(編集ロック) → 両者READY → ホスト開始で原子的ロック → 準備10秒(戦闘デッキ不変) → 試合中 → 終了 → 再戦ロビー(編集可)`

- 編集変更時：もし以前readyなら、デッキ変更とready解除を一つの提出更新で実施。編集が不完全な時点でreadyを押せない。
- 不完全なデッキ・重複・未知のID・相手のID・前ラウンド・デッキリビジョンの食い違い → 開始拒否、理由を表示。
- 片方がルーム退出／BOT席への切替 → 対象席のreadyを外し、別の`seatId`が入ったら旧デッキ承認を引き継がない。
- 切断復帰：既存の`clientId`はページ再読込で変わり得る。新しい「自動再占席」を本機能だけで保証しない。**少なくともデッキ実装で現在の復帰挙動を悪化させず、同ルーム再戦と別ルーム入室を区別してテスト。**
- 再戦：旧`lockedDecks`を新ラウンドの承認デッキに無条件流用しない。ローカルの直前編成を下書きとして表示、双方もう一度準備完了で新ラウンドのlockを取る。BOT自動READYは合法なデッキ送信とセットにする。

## 6. BOT・保存の境界

- **通信不要ソロBOT**は既存10枚固定循環のまま初期版では保護。オンラインデッキ構築の作業によってBOTが10枚→8枚に無断変更されないようにする。
- **オンラインホストがBOT参加**させる場合は、BOT側に合法な初期8枚プリセットを自動設定し、BOTが未提出状態でREADYになることを防ぐ。ゲストBOTモードはその席で選んだ8枚の範囲に行動を制限。特定カードIDを前提としたBOTの選択は欠落カードを必ずスキップする。性能の強化は別案件。
- **localStorageは必須にしない**。Google Sitesの埋込`iframe`やSafariでは保存領域の挙動が環境依存。読書きは`try/catch`＋schema/versionチェック。保存不可ならメモリ上の下書き＋初期標準編成で遊ぶ。保存を有効にするためのアクセス許可ダイアログを必須にしない。
- ローカル保存時は同一端末で利用者が交替することもあるので、**個人情報・固定ユーザー名なし**。保存フォーマットの破損は破棄して標準に戻す。
- `localStorage`が失われたときに既存ルームの戦闘デッキが消えないこと。ただし再読込後に参加席を取り戻せるかは現在の接続仕様の別問題。

## 7. 実装開始前に揃える品質ゲート（設計のみ・未実行）

### デッキ定義テスト
- 8種類→成功、7/9種類→拒否、重複ID／歩兵混入／未知ID／空値／不正バージョン／旧ラウンド→拒否。
- 片側は大型0、片側はスペル0、両方の8枚が重なりなし等の合法な偏りでも選択可能。警告は自由度を阻害しない。
- 次のカード補充、使用回数枯渇、0〜4枚手札、常設歩兵、コスト不足、左右非対称、シャッフル・再戦シャッフルの再現テスト。

### 同時操作テスト
- 編集→準備完了、準備解除→編集、両者READY、開始ボタン連打、双方同時READY変更、開始直前編集、退出と新席ID、ゲストの遅延パケット、BOT参加と退出、途中通信切断、再戦ラウンド分離。
- ホストに誤ったcard IDを送っても使われず、エネルギーや使用回数が減らない。
- 古い版の参加者と新しい版の開始を一貫して拒否、理由表示。
- 対戦開始後にロビー下書きやデッキプリセットを書き換えても、進行中の`S.hand/S.queue`に影響しない。

### 画面・体感テスト
- 学校iPad横持ちSafari/Google Sites、狭い埋込枠、別方向からの再入室。カード絵とタップ領域、誤操作、8/8確認、詳細表示、準備ボタン有効化の一致。
- 手札5枠の既存見やすさ／タップ応答とデッキ編集の処理負荷。カードを触るたびに高コストなCanvas肖像を全再描画しない。
- 2端末Firebase実接続、ホストとゲスト双方の反映遅延、再戦、切断、ロビーでの編成同期。Rules変更の要否を検証しても**稼働中のFirebase Rulesを勝手に更新しない**。

## 8. この時点の推奨採用と未確定

### 本人の方向性として固定
- 基本歩兵常設、選択カード8枚、対戦中4枚手札（既存方式を原則維持）。

### この文書で新規提案・未承認
- 選択8枚は重複禁止、ユニット/スペル自由、特殊育成なし。
- 初期から8/8の標準編成を表示し、入れ替え主体の操作。
- 準備完了で編成固定、再戦で編集解除、同ラウンド原子的ロック。
- オンラインのBOT席には合法な8枚初期セット、ソロBOTは既存10枚維持。
- 再戦時のデッキ再承認、保存は任意で非必須。

### 次の設計レビューで聞く価値がある論点（コードは引き続き変更しない）
1. **同カードの複数枚採用を認めるか**：おすすめは禁止。後から重複採用を許す場合、カード使用回数と手札サイクルの意味を再設計する必要がある。
2. **編成編集を準備完了前のみでよいか**。おすすめはYES。準備10秒中の入替は混乱を招く。
3. **プリセット保存を初版から必要とするか**：おすすめは「直前の1つ＋標準に戻す」だけ。保存できない端末でも遊べる。
