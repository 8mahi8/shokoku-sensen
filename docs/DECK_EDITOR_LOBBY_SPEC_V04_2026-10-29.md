# 小国戦線III｜デッキ編集画面・対戦ロビー設計 V0.4（2026-10-29）

> 状態：**設計案のみ。ゲーム本体・UI・通信・Firebase Rules・公開版は実装・変更しない。**
> 本人の確定方針：**基本歩兵は常設／デッキは異なる10種類／同カード重複なし**。2026-10-29 V0.3より後の議論なので、この設計の枚数は10固定。キャラ追加は後工程。

## 1. 現状監査と設計の狙い

- 開発ブランチ perf/online-guest-snapshot-diagnostics-20261020、Draft PR #22。現行コード online-game.js は固定DECK_IDSの10種類を各軍シャッフルし、HAND_SIZE=4、常設infantry＋手札4枚の5枠。S.hand/S.queue/S.leftとadvanceHandが循環・残使用回数を管理。
- online-net.js は ROOM_VERSION=2、players/host|guest/ready の準備状態と meta/status の試合開始が別ノード。ready() は前者を書き、startMatch() はmetaだけのtransactionを実行。新しい選択デッキを追加するには**同時操作を安全に扱う状態設計が必要**。
- online.html の現行オンラインダイアログは最大幅約510px・縦方向スクロール。10枚＋カタログ一覧を詰め込むには不向き。
- 現在の編成候補はちょうど10種類（歩兵以外の8兵種＋2スペル）なので、現状の合法な編成は一通りだけ。11種類目以降が増えて初めて入替の意味が生まれる。キャラの追加を先走らない。
- デッキUIは**新キャラの追加後に自動で一覧が増える**ことを目的とする。別のカード名リストを持たない。

## 2. 編集UIの画面設計（提案）

### ロビーと専用編集画面を分離

ロビーは従来の「部屋を作成・5桁番号で参加」「青／赤の接続・準備状態」「自分のデッキ10/10」「デッキを見る／編集」「準備完了」「ホストの対戦スタート」という小さい画面を維持。

デッキ編集時だけ全画面に近い独立したオーバーレイを表示。ゲームの戦場・5枚手札HUDを裏で操作させない。

iPad横向き時の配置案：
- ヘッダー：デッキ編集、選択10/10、戻る。
- 左：現在の採用10種類を5列×2段でカード画像・名前・コスト付きで表示。
- 右：全編成候補を一覧表示。採用中／未採用を視覚的に分け、増加時は一覧ペインだけスクロール。
- 下部固定：基本歩兵は常設、平均コスト（選択した10種類のみ）、対空／占領役・スペル数など簡潔な概要、標準に戻す、保存して戻る。
- 画面の高さが低いGoogle Sites埋込や縦画面では二段レイアウト／タブ式に切り替え、閉じる・確定ボタンを下端に置く。小さい文字や押しにくい10枚横一列を避ける。
- 主要タップ領域は概ね44pt以上、描画更新中の誤タップ防止。画像生成は初回描画と変更カード分だけにし、編集ボタン操作ごとに全ての肖像Canvasを再作成しない。

### 入替の操作

- 初期は常に合法な**10/10選択済み**のデッキを持たせる。初回に10回選ばせない。候補が10種類しかない時は「全10種類を採用中。新キャラが追加されると入れ替えできます」と表示。
- 候補が11種類以上になったら、**未採用カードを1タップ→採用中の交換対象を1タップ**で置換。全操作中、採用数は10のまま。同カード重複と空欄は作れない。
- 交換待ちは選択ハイライト＋「入れ替えるカードを選択」という案内を表示。再度タップ／キャンセル／閉じるで解除。ドラッグ操作は必須にしない。
- 能力説明はカード上の明確な「詳細」ボタン（または長押し）で開く。入替タップと競合しないようにする。
- 標準に戻すは、候補数が増えても既知の標準10種類を復元する。初版で複数デッキ枠、共有コード、カードレベル、課金・アンロックは不要。
- 「保存して戻る」は**この端末の編集下書きを確定するだけ**で、対戦ルームの準備完了ではない。変更破棄で戻るも可能。準備完了後は先に準備解除が必要。

### 補助表示

平均コストは常設歩兵の2を入れない。対空可能なカード0、重コスト偏重、占領が常設歩兵だけ等は**警告に留め、編成自体は禁止しない**。スペルは選択対象に含み、必須採用枚数や上限は現状設けない案。初版は役割別の簡単な分類のみで複雑な絞込は不要。

## 3. ルームロビーの状態遷移（提案）

1. 未参加：作成／参加／BOT練習。
2. ロビー入室：自分の保存済みまたは標準10種類を下書きとして表示。相手の接続と準備状態のみ表示し、相手の採用カードはUIで露出しない。
3. 編集：ローカル下書きの交換。まだサーバーのREADYは変えない。
4. 準備完了を押す：**選んだ10種類・席ID・ラウンド・版数をまとめて提出**。サーバーから確定が取れたらREADYとして表示。送信失敗では成功表示を出さず、下書きは残す。
5. 準備解除：サーバーでREADYをfalseにしてから編集可能とする。開始ボタン連打や編集途中の開始を防ぐ。
6. 青赤ともREADY：青ホストにのみ開始ボタン表示。スタート押下時に両者のREADYと選択10種類を同時検証して固定。
7. 準備10秒・対戦：ロックした10種類をそれぞれ独立にシャッフル、手札4＋待機6。残回数があれば使ったカードを列末尾へ。基本歩兵は常設。
8. 結果／再戦：ホストがラウンドを進め、両者のREADY解除・前ラウンドのロック失効。**直前の編成は下書きとして復元**。ゲストは現行同様ホストを待つ。

ロビー画面の文言例：
- 青軍：準備完了／準備前／接続待ち
- 赤軍：準備完了／準備前／接続待ち
- 自分のデッキ：10/10種類、デッキを見る／編集
- 自分：準備完了（送信中は押せない）→準備解除
- ホスト：対戦開始（双方の準備をサーバーで確認した場合のみ）
- ゲスト：ホストの対戦開始を待っています

**相手のカード非表示はUI上の非表示であり、Firebase DBに保存したデータの暗号学的秘匿ではない。** 身内1vs1に必要な公平・安定性を優先する。

## 4. カタログとデッキ機能の責務分離

- CATALOG（CLASSES＋SPELLS）がカード名・コスト・種類・特性の**唯一の正本**。編集画面専用の兵種リストや性能コピーを作らない。
- 編成可能フラグ（仮称 deckEligible）で常設infantry、未公開・テスト専用カードを除外。新キャラがAI・アート・攻撃演出・学校HTMLのQAを通ったらフラグ有効化で自動的にカード一覧へ現れる。
- DeckRules: permanent=infantry、chooseCount=10、handSize=4、unique=true を共通定義。
- DeckValidator: 配列、長さ10、ID全件既知・編成可能、重複なし、歩兵なし、バージョン適合。ホストが必ずもう一度検証する。
- DeckDraft: 編集中の10種類。ReadyDeck: ルームの席とラウンド付き提出済み10種類。MatchDeck: ホストが試合開始時にロックした不変の10種類。ゲームのhand/queue/leftはMatchDeckから生成。
- 新キャラに伴ってデッキUI、オンライン同期、ターゲットAIへ「このIDなら」という分岐を追加しない。BOTの特定ID依存は別の既知課題。
- DECK_IDSは従来の標準10種類プリセット／回帰比較の参照に使えるが、**候補カードの総数を10に制限する目的では使わない**。

## 5. RTDBでの準備完了と対戦開始

現行コードでは players.ready と meta.status が別々に更新され、開始の瞬間にデッキとREADYの整合性を一括保証できない。設計案は**meta配下のロビー確定を単一のトランザクション領域に置く**こと。

データ形（仮）：
- meta.version: 新しいルーム互換性番号（現状は2）
- meta.status: lobby / playing / finished
- meta.round: ラウンド番号
- meta.lobby.host: {seatId, revision, ready, deckIds: [10 IDs]}
- meta.lobby.guest: {seatId, revision, ready, deckIds: [10 IDs]}
- meta.lockedDecks: {round, hostSeatId, guestSeatId, version, hostDeckIds, guestDeckIds}
- players.host/guest: 現行の参加ID／online状態を継続管理
- state/commands: 現行の高頻度戦闘世界・操作は変更しない

手続：
- 入室・ゲスト席交替・ホストBOT席の切替では、meta.lobbyの**seatIdとREADYを紐づけ**、他人の前ラウンドデッキを引き継がない。
- READY切替もmeta領域のトランザクション。編集確定時の10ID、revision、roundと同じデータに記録。旧players.readyを別の権威として併用しない。
- 試合開始はmetaトランザクション内で、status=lobby・当ラウンド・両seatId・両READY・10種類の妥当性・versionを再判定し、status=playingとlockedDecksを**同一コミットで決定**。
- ロビー／再戦操作で同じmeta領域に直接のset/updateとtransactionを混在させず、状態変更を統一する。Firebaseは同じ場所のsetが進行中のtransactionをキャンセルし得る。
- playersにある入室・presence情報とmeta内の席登録が別場所なので、**これだけで座席確保まで完全に原子的になるとは言えない**。入席の二段階確認、異常終了時の修復、開始直前のplayers.idとmeta.lobby.seatId照合、オンライン確認を実装時の必須検証にする。開始瞬間の不可避の切断は従来の接続回復の範囲。
- ホストはロック済みデッキを受け取ってからgame.beginを実行。失敗時に「なんとなく固定10種」で開始してゲストと食い違わせない。
- 試合中は頻繁にデッキ全体を送信しない。既存のhand/queue/leftを同期。
- ゲストから非採用IDの召喚要求が来ても、ホストがMatchDeckと手札／コスト／上限を検証して拒否。対戦中の下書き変更は無視。
- 旧クライアントと新クライアントの組合せで対戦開始しないようにルーム版数で互換性判定し、更新案内を表示する。

## 6. 保存・BOT・再戦で特に守る点

- 初回は現在の10種類をすべて選択済み。11種類目以降の追加後も保存した10種類が合法なら維持。
- localStorageは任意・例外を捕捉・保存破損や使用不可IDがあれば標準カードで不足を補充して**10種類に自動修復**。永続化できなくても現在のセッション内で遊べる。Google Sites iframe／Safariでブラウザ保存を必須条件にしない。
- ソロBOTは現行固定10種類を維持し、オンラインデッキ選択の導入と一緒にBOTの大規模AIを書き換えない。
- オンラインでホストがBOT席を追加する際は、その席に合法な10種類を自動提出してREADYと連動。ゲストがBOT操作に切替えた場合は**そのゲスト席の10種類のまま**操作させる。
- 再戦は前回デッキを下書きとして残すが、READYは新ラウンドで再提出。古いlockedDecksを新ラウンドへ持ち込まない。
- ユーザーID・デッキ名登録、複数プリセット、ユーザーログインは初版対象外。

## 7. 実装前に必要なテスト設計（まだ実施しない）

1. 枚数10、すべて異なる、歩兵なし。9/11種類、重複、未知ID、未公開IDは拒否。11種類目のテスト専用仮キャラは自動で一覧に現れ、交換対象になり、他キャラのAIを壊さない。
2. 現行10種類と新システムの初期手札4・待機6・カード使用回数・スペル・歩兵常設の互換性確認。
3. 二人同時READY／READY解除／開始連打／入席交替／BOTの出入り／切断と再接続／再戦のラウンド隔離／古い版の参加をFirebase Emulatorで検証。
4. Chromium/WebKitで編集画面、タップ操作・低いGoogle Sites枠・縦横回転、誤操作・表示崩れ・描画負荷を確認。
5. 実Firebaseの2ブラウザでロビー→準備完了→開始→戦闘→再戦を検証。学校iPad Safariの体感は別の実機検証。公開版main、学校安定版、Firebase Rulesは本人の指示なしで触らない。
