# 小国戦線III｜ゲームシステムのホスト／ゲスト公平性監査（2026-10-23）

## 前提と対象

- **Google Sites版：ユーザー申告による「再戦修正版」**。Git commit `53f8bcc55037b8ae051560504274388e02cb8c41` の `online-ipad.html`、Git blob `f2256b16061de4390ff121f9cbc3a5c0b33b9a26` を調査ベースラインとした。コンテナ内のHTML実物314,212バイトについてGit blob SHAの一致を確認。**実際の埋め込みHTMLそのものをサイトから照合したわけではない**。
- **開発版：エネルギーゲージ追加版**。Git blob `bc89bca4cd9621ec03fdd2ca2f8f97d0364435be`、315,713バイトでも同一の実行監査を実施し、下記のゲームシステム問題が残っていることを確認。
- **今回の操作：調査、実コード関数を抜き出したNode検証、既存CI結果の照合、この文書のみ**。ゲーム本体、学校Google Sites、main、Firebaseの設定・既存ルームは変更していない。
- **対象：人間ホスト（青軍）vs人間ゲスト（赤軍）**。BOTの賢さよりも、プレイヤー間で実際の戦闘挙動・操作受付・時間管理が公平かを評価した。

## 発見した問題（優先順）

### A｜人間プレイヤーの部隊AIが青軍／赤軍で異なる【確定／ゲームルールに影響】

`online-game.js:getFort(u)` で、`d.behavior==="capture"` の兵士（偵察ライダーと重装工兵）が目指す前哨基地の順序が以下のように分岐する。

```js
if(u.team===2&&S.difficulty!=="easy")options.sort((a,b)=>b.x-a.x);
else options.sort((a,b)=>direction*(b.x-a.x));
```

- 青軍では、前方の候補のうち **より敵陣奥** を優先する。
- 赤軍では通常／むずかしい難易度で **より自陣寄り** を優先する。
- コメント上は「強いBOTは近い基地を優先」とあるが、**処理はBOTだけに限定されておらず、人間が召喚した赤軍兵にも適用**される。
- 再戦修正版から抽出した実関数を実行し、青軍 `x=600,y=300` と赤軍 `x=680,y=300`（左右対応する位置）の偵察ライダーで、候補が青軍 **x=867**／赤軍 **x=633** となることを再現。赤軍の難易度を練習に変えると **x=410** となる。重装工兵でも同じ。
- これは演出上の違いではなく、前哨基地占領、召喚ライン、相手の動きへ影響する。**最優先で仕様方針を明確化するべき不一致**。ただし、マップが完全な左右対称ではないので「目標のxを左右反転すれば常に同一」という単純修正は避け、同じ距離／進軍方針を目指す。

### B｜非基本カードの使用後、ゲストだけ内部選択が残る【確定／操作不一致】

- ホストの `deploy()`／`castSpell()` は、カード使用成功時に `S.selected` を基本歩兵なら保持、その他では `null` にする。
- ゲストの `playCard()` は `NET.sendCommand()` を送って即 `true` を返し、選択解除をしない。`apply()` は次の受信時にも `S.selected=oldSelected` として元の選択を復元する。
- **実コードの`apply`コールバックをスタブ環境で実行**し、手札からscoutが消えてarcherに替わったのに `selected="scout"` が残ることを再現。見た目上は選択ハイライトがなくても、戦場の次のタップで古いカードを実行しようとする可能性がある。
- 修正時は、手札にないカードの選択解除と、通信中の保留命令・失敗通知を同時に検討する。

### C｜ゲスト連打のローカル受理／失敗通知欠落【確定したコード上の挙動。実機発生頻度は未測定】

- `sendCommand` はFirebaseへ非同期push、`playCard` のゲスト側はローカルの `canPay` 条件だけで成功扱い。実処理は後でホストが検証する。
- **実`deploy`と`playCard`関数による同一残量テスト**：エネルギー2、基本歩兵コスト2、短時間の2回連続操作 → ホストは1回成功・2回目却下・エネルギー0・2体生成。ゲストはローカルでは2回とも成功扱い・エネルギー2のまま・命令2件送信（ホスト側で2回目を却下する見込み）。
- ゲストの通知受信は `feedback?.seq===commandSeq` の場合だけ表示するため、連打で新しいseqが発行されたあと、前の命令の却下通知は表示されないことがある。
- **ゲストも本来、ホストと同じカードを同じコストで使える**。問題は応答確認・手札とエネルギーの反映タイミング、および失敗理由の分かりにくさ。連打可能な操作条件の取り決めとpending命令管理、命令ごとの結果通知を検討。

### D｜ホストFPSに戦闘時間全体が依存する【構造的リスク／学校実機での発生は未測定】

- 戦闘はホストだけが`tick(S.speed/30)`を行い、ゲストは状態受信のみ。
- ホストの各描画フレームで `delta=Math.min(.09,(now-previous)/1000)`（負値も0に制限）として時間を積算。ホストの描画が低下し、1フレーム間隔が90msを超えると実時間を切り捨てる。
- 元のフレーム処理相当で実時間60秒を模擬した結果：60FPS→ゲーム60秒、30FPS→60秒、15FPS→60秒、10FPS→約54秒、5FPS→約27秒、2FPS→約10.8秒。
- 低FPSなホストでは、**ゲーム内の時間、エネルギー回復、兵士の移動と戦闘が両プレイヤーとも遅くなり得る**。これはゲストの画面だけのカクつきとは別。ホストをバックグラウンドにすると顕著になる可能性。
- 解決策はフレームから独立したゲーム時計・適切なcatch-up／負荷制御だが、オンライン安定性を壊し得るため**測定なしの大改造はしない**。

### E｜開始条件は同じだが、配られる手札とマップは厳密な鏡像ではない【既存仕様／小さな非対称】

- デッキは双方共通のカード候補から**別々にシャッフル**し、同一の開始4枚・順序にならないよう再抽選する設計。これはホスト特権ではないが、全く同じ条件ではない。
- 前哨基地座標は `(410,190)`／`(633,444)`／`(867,205)`。左右反転時、端のxは410⇔870に対して赤は867（3差）、端のyは190⇔205（15差）、中央xは633⇔647（14差）と微妙に異なる。意図不明。ゲームプレイの支配的要因かは未測定。

## 確認できた「同じルール」

- **基本召喚可能範囲**：青軍x≤244、赤軍x≥1036。基準1280幅の左右反転で10点の可否を検査し一致。
- **使用可能エネルギー判定**：同一`canPay`関数。エネルギー2なら両陣営ともコスト2を使用可・コスト3を不可、エネルギー3なら両陣営ともコスト3可。
- **カード使用回数と手札回転**：同一`advanceHand`実関数。同一手札とキューを与えたとき両チーム同じ結果。ホストが全員分の限度回数を検証。
- **回復速度**：ホストで両チーム同一`rate()`／`tick()`。区間は0–100秒0.25、100–210秒0.36、210–270秒0.53、270秒以降0.7（ゲーム秒当たり）。
- **攻撃・防御・HP**：両陣営ともホストの同じ`unitStep`／`spellStep`／`hitUnit`で解決。色別のHPや攻撃力倍率は認められない。
- **決着**：ホストで勝者を確定し、ゲストは`resultForMe()`で自分のチームに換算。時間切れは首都HP割合で比較。
- **Firebaseオンライン基本動作**：既存CI [#39912333435](https://github.com/8mahi8/shokoku-sensen/actions/runs/39912333435) でChromium/WebKit、WebKit/WebKitの実Firebase 1vs1、連続再戦、切断復帰等が成功。ただし、各操作の同時性／学校iPad実機上の公平性の証明ではない。

## 補足：未証明の公平性リスク

- ホストは操作をローカルで即処理、ゲストはFirebase送信→ホスト確認→ゲスト受信。試合開始直後、前哨基地獲得の直後、カード連打やギリギリの資源消費で、体感上ホストが先行する可能性がある。**具体的な一方向遅延は未測定**。
- `unitStep()`は`S.units`を並び順に処理し、相手のHPを即更新。相討ちのごく短い競合で**先に配列へ入った兵が先に攻撃する**可能性がある。ネットワーク経路と結び付く優位性の有無は別テストが必要。
- ユーザーのGoogle Sites版は直接HTML埋め込みであり、GitHub Pagesを貼り込んでいるわけではない。コードのGit SHAと実サイトHTMLが厳密に一致することはサイト現物未取得のため証明していない。

## 次フェーズの優先順位（今回は未実装）

1. **Aを最優先で修正候補化**。人間の青・赤兵が同じルールに従い、BOTだけに難易度依存のAIを適用する。複数拠点候補と双方の最前線で差をテストする。
2. **B+Cをひとまとめで修正候補化**。ゲストカード選択の同期／連打時pendingとホスト拒否／ユーザーへの適切な通知。再戦をまたぐ未処理命令の失効もテスト。
3. **Dを独立検証**。ホスト15/10/5FPS相当の制限を入れ、ゲーム時計・エネルギー・兵士座標を実時間と比較。同じ学校iPad実機の交代テストで採否を決める。
4. Eの地形調整や完全同一手札は**ゲームデザイン判断が必要**。勝手に変更しない。
5. 各修正は開発ブランチのみ。学校で貼り付ける版は**ユーザーが「貼った」と明言したときだけ更新**。本番/mainへの自動反映はしない。
