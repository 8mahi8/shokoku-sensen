# 小国戦線III｜エネルギー使用可とホスト時計の時間差を測る検証（2026-10-23）

## 前提：公開版を変更しない

- Google Sites版＝ユーザーが貼り付けて遊んでいる「再戦修正版」のまま。今回テスト準備・自動実行のみ。
- 開発ブランチ `perf/online-guest-snapshot-diagnostics-20261020` に開発テストを追加。最新のエネルギーゲージ補間・ゲスト選択解除・部隊AI統一は保持。
- 正式な戦闘進行・エネルギー使用可判定・通信命令の仕様は変更しない。
- `__shokokuQa.setEnergyForQa` は **localhost / 127.0.0.1 かつ ?qa=1 のみで登録**されるデバッグ専用メソッド。本番SitesにはUIも操作入口もない。

## 実Firebase計測の設計

- 既存 `tests/online-guest-lab.cjs` で使う、使い捨てFirebase部屋の「青軍BOTホスト×赤軍手動ゲスト」を利用。
- ゲストHUDが受信中に小数値を先読みし、受信停止時350msを超えて進まない既存の合格試験を保持。
- 続いてホストQAで赤軍のエネルギーを1.65に設定し、正式な状態スナップショットの受信後、**コスト2のカードが使える境界を両端末がいつ認識するか**25ms間隔で測定する。
- ホストが最初にエネルギー2へ到達した瞬間、ゲストの確定エネルギー、双方が2へ到達した時刻、差分（ms）を出力。これは**操作の入力遅延測定ではない**（ゲスト画面での実タップ／ホスト受領と区別）。
- 同じ区間で、ホストのゲーム経過秒とブラウザーの実経過秒を比較する。Linuxのheadless WebKitは低FPSになりがちなため、絶対値を学校のiPadに一般化しない。
- ラグ値4秒以下はテスト暴走／完全凍結の防止という粗いガードであり、快適さの合格基準ではない。
- **録画・結果以外のユーザー対戦履歴や試合ログは収集しない**。使い捨てルームのFirebaseデータは終了時に削除。

## 時計の大改修をしない理由

現在、ホストは `requestAnimationFrame` ごとに最大90msの経過時間を扱い、30Hz固定刻みで最大5tickだけ進める。長いフレーム停止によりゲーム秒が失われる可能性は明確だが、catch-up上限を単に増やすと、CPUが混雑している端末で余計に処理を増やし、連続してFPS低下する危険がある。Gaffer On Games / Fix Your Timestep: https://gafferongames.com/post/fix_your_timestep/ 。またSafariではバックグラウンドのiframeのrAFが制限され得る: https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame 。実測に基づいて変更を決める。
