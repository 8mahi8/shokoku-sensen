# 小国戦線III｜V15 ゲスト停止・描画カクつき・対空とドローン耐久（2026-10-19）

## 発端と範囲

本人が**公開版**をPCとiPadで対戦した際、ゲスト側がフリーズすることがあり、動作もカクつくと報告。また飛行ユニットの当たり判定が武器の見た目と合わず、ファイヤー（現ゲームでは範囲砲撃）でドローンを倒したいとの要望。本人は「公開版で症状が出たのだから、開発版の修正状況を調べるべき」「砲撃を強化するよりドローンのHPを下げる」と明確化。

作業は**developのみ**。公開mainや公開GitHub Pagesを変更していない。実端末へのOTA更新、学校iPad上での動作実測は行っていない。

## 原因と改修

### 既存開発版の状態

- developには画面外カリング、遠景のキャラクター描画キャッシュ、低FPS時の高解像度canvas縮小が既に導入されていた。ただしホストからのFirebaseフル状態送信は約180ms周期（5.6Hz）で、ゲスト側は各受信状態を即座に反映していた。
- 特に重要な実装上の問題：`drawUnit` にはゲスト側の位置補間があったが、`renderCrowdedUnit` で**キャラクター画像キャッシュを使うときは補間を経由せず受信座標 `u.x/u.y` で描画していた**。そのため大量のユニットが映る場面では、画面描画のFPSが高くても兵士の移動がネットワーク更新の度に飛び飛びに見える。コード上この経路を確認し修正した。
- freezeそのものは単一の再現手順を特定できていない。通信途絶、端末性能、Safariによるタブ制限、描画負荷のどれが主原因かの断定は避ける。

### developへ入れた修正

- `online-net.js`: 受信側は最新の有効seqだけ保持し、次の `requestAnimationFrame` に**一度だけ最新のsnapshotを適用**。古いパケットを大量に反映しない。新ルーム/再戦/離脱で保留データを消去。ホスト側はFirebase `state.set` の送信中に別の定期送信を溜めず、必要な強制送信は合流・遅延させる。**ホストが唯一の権威であること、ゲストの合法な召喚はホストが検査することは従来のまま**。
- `online-game.js`: ゲスト側iPad相当のキャンバスDPRは**1.0**に固定し、画素総数を削減。低FPSを観測したゲストでは約30fpsの描画間引きでメインスレッド負荷を抑制。画面のHUD更新は120msの通常ループに任せ、Firebaseパケット受信時に毎回DOM更新しない（フェーズ変更時を除く）。
- 同ファイル：大規模戦闘でiPad側ゲストが受け取る遠景表示は巨大ユニットでも絵柄付きポーズタイルキャッシュが利用可能。大量描画時だけ爆発の装飾線/投射物のshadowBlurなどを軽量化。通常時は元の美観・演出を維持。
- **本質的なゲストのガクガク対策**：`presentRemoteUnit(u)` を導入し、`drawUnit` と**キャッシュ使用時の `renderCrowdedUnit` の両方で同じ位置補間**を使う。戦闘判定・攻撃対象・敵の位置・サーバー側の状態には影響しない。

### 対空とファイヤー

- 浮遊ドローン `hp:135 → 120`。範囲砲撃ダメージ`125`は**変更せず**、範囲内のHP満タンのドローンを一撃で撃破する。
- `hitAir:true`：従来の魔導射手に加えて、射撃・砲撃が見た目にも届く**制圧機兵、魔導重戦車、浮遊ドローン自身**。それぞれの通常射程・クールダウン・資源コスト・その他耐久は変更しない。
- **近接のみ**の基本歩兵、偵察ライダー、重装工兵、迎撃衛士、守護ゴーレムは対空不可を維持。物理的な攻撃可能性に基づき、全ユニットを一律対空にはしない。
- 仕様記述 `note` も更新済み。

### 配布ソース整合

- `online.html` は単体の `online-game.js` と `online-net.js` を参照。
- `online-ipad.html` と `online-embed.html` は、両JSをHTML内に埋め込むため**最新ソースを同期更新**し、古い処理が残らないようにした。

## 実際に通過した検証

1. [V15 WebKit/Chromiumでの受信ストレス・対空検証 #39145440797](https://github.com/8mahi8/shokoku-sensen/actions/runs/39145440797) **SUCCESS**。130体の実ゲーム兵士データを1回のフレームまでに120パケット送り、120の最新版だけ最終適用されることを確認。続いて約75ms間隔のパケットを149まで継続送信し、いずれのブラウザも最後まで受信・描画が進み、pageerrorなし。4構成（Chromium/WebKit × iPad横相当1194×834 / 小窓相当900×520）でチェック。WebKitではCPU/GPUの差があるため、実機のfpsと等値ではない。
2. 同テストで、**キャッシュされた兵士が実際に中間座標を通る**ことを確認。受信位置の例 `x=250 → target=300` に対し、WebKitで約`x=284`、Chromiumで約`x=298–301`に進んだ。従来はキャッシュ経路で補間関数自体が呼ばれず、移動表示がスナップショット間で跳んだ。
3. 同テストで、`drone.hp=120`、`barrage.damage=125`、完全HPのドローンが砲撃後に0体になること、魔導射手・制圧機兵・魔導重戦車・ドローンが実戦エンジン上でドローンへダメージを与えること、基本歩兵・迎撃衛士は対空不可のままであることを検証。
4. [開発版の実Firebase 2ブラウザE2E #39145202391](https://github.com/8mahi8/shokoku-sensen/actions/runs/39145202391) **SUCCESS**。参加／準備／ホスト試合開始／ホストからゲストへ戦況同期／ゲストのBOT制御切替／ゲストの手動召喚を実際のFirebase上で確認し、試験専用ルームは終了後に削除。こちらは**Chromiumの2ブラウザ**であり、WebKitの実Firebase対戦ではない。
5. [最新全体オンラインsmoke #39145213573](https://github.com/8mahi8/shokoku-sensen/actions/runs/39145213573) **SUCCESS**。JS構文、HTMLへ組み込んだbundle整合、手札、ラウンド／再戦／ルームの判定など。途中、rAF遅延受信に対応するためローカルFirebase模擬試験 `tests/online-sim.cjs` にrAF模擬を追加。旧bundle不整合により失敗した途中のrunは最新の同一ソース同期後に解消した。

## 残るリスクと実機受け入れ条件

- CIヘッドレスWebKitと**学校iPad Safariの性能/権限/埋め込みGoogle Sites CSPは異なる**。現時点で「実機で100%フリーズしない」とは言わない。
- WebKit/Chromiumの密集130体描画でも一部スローフレームが残る可能性。描画品質と安定性の折衷は実機で調整。
- ユーザーが公開版で確認したフリーズはまだ再現できておらず、今回の修正が**すべての原因を除去した証拠ではない**。
- **公開main・GitHub Pagesは引き続き旧版**。developで試作成功しただけで、公開して友達の端末へ届いたわけではない。公開版へ反映する際は二者でのiPad+PC対戦、ゲームの同期・手動召喚・再戦・描画の安定性を改めて確認し、本人による公開承認に沿って進める。
