## 1. 実験方法と「何が本物か」

`tests/online-unit-ai-firebase-e2e.cjs`を新設。通常の2ブラウザRTDBルームを作り、両プレイヤーが新5体を含む各10種類のデッキでREADY→ホストがロック→対戦開始。両ブラウザとも実際の`battle`進行を確認。

**AIテスト用戦況を再現可能にするため、localhostから配信するときだけ`online-game.js`と学校用HTMLのHTTP応答文字列にテスト専用APIをメモリ内挿入した。元ファイルには書き込まない。** 兵士・砦の位置と一部初期HP、最初の攻撃準備状態、場面転換時の対象退場などはテスト用に固定する。一方、`selectPriorityTargets`・`unitStep`・`fire`・30Hzの進行・Firebase送信・WebKitゲストの受信/描画はゲーム本体の実処理をそのまま使う。

従って「固定戦況で新AIがオンライン対戦エンジン上で期待どおり動く」証明であり、「自然に20枚召喚した試合のすべての競合・性能・バランスが完璧」だという証明ではない。実タップ召喚は前述の別E2Eで補完する。

## 2. 結果：8場面すべて実際のhost tick＋guest同期でPASS

| 場面 | 合格した実際の結果 |
|---|---|
| 遠距離工兵（青軍） | 近い敵兵より優先度3の砦を攻撃、砦を青所有へ占領、その後敵兵を攻撃しHP 105→75 |
| 遠距離工兵（赤軍） | 左右入替の赤軍でも同じ優先ルール。砦を赤所有にし敵歩兵HP 105→75 |
| 迅速迎撃騎兵・追跡帰還 | アンカー中心索敵円に入った敵を追う。敵が円外へ移動すると追尾をやめ、開始地点300付近（x=306.27、停止半径7内）へ帰還 |
| 迅速迎撃騎兵・円外自衛 | 敵が固定索敵円外でも自身の攻撃射程内なら追わずに反撃。位置x=480維持、敵HP 105→67 |
| 守護ゴーレム・大型優先 | 近い歩兵より大型戦車へ先に115ダメージ（歩兵へ範囲ダメージも仕様どおり）。大型をテスト操作で退場させると攻撃候補を歩兵に再選択 |
| 重撃砕兵・大型特別扱いなし | 近い歩兵を150攻撃で撃破。後方の大型ゴーレムHP1400は変化せず、歩兵除去後に大型を次の攻撃候補へ選択 |
| 双剣兵・連撃 | 0.55秒間隔の22ダメージ攻撃を2発確認。敵HP 105→61、射程内では移動せず戦闘 |
| 対地爆撃翼・対地範囲 | 主対象55ダメージ、隣の地上兵33、飛行ドローン0。敵飛行を攻撃候補にしない |

各場面で**ゲストのキャラ位置・実HP・砦の所有状態をホストと独立照合**。該当場面の値がWebKitへ同期されるまで待機し、Canvasのページエラーも確認。ホスト／ゲストそれぞれ8枚、計16画面を保存し、目視レビューで戦場・HUD・新キャラの大きな欠落なし。双方が同じ陣営色で表示されない場合があるのは自軍／敵軍視点の相対配色であり、状態値の同期不一致ではない。大型による小型の隠蔽は本人承認の戦術であり勝手に透明化しない。

## 4. 限界・次工程

- AIが固定配置で設計通りなのは確認済み。ただし「5分間の自然対人対戦で新5体全員の判断が常に快適」「学校iPad実機でエフェクトも滑らか」「BOTが新5体を使いこなす」ことは未確認。
- テストシーンは本当のカード消費やゲーム内の自然な遭遇を再現する目的ではない。デッキ選択・カードタップ・オンラインコマンドは別の成功E2E `tests/online-deck-online-e2e.cjs` の根拠を使う。
- 新AI・通信基盤を改造してから再テストするのではなく、既存の成功を保存し、自然な試合での操作・UI・性能・対戦バランスの検証に進む。以前の学校実機ラグ合格候補は別版（学校安定版）での評価なので、新デッキ統合版の学校iPad/Google Sitesでの最終実機判断は本人の試遊を待つ。
- CIのLinux headless WebKit FPSは物理iPadのFPSの代用ではない。長時間ブラウザクラッシュ問題 `#40864184371` がこの約30秒テストで根治したとは主張しない。
