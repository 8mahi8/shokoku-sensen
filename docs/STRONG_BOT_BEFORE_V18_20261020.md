**V18の戦闘演出・操作UI強化は一時保留**。その前に、1vs1で「プレイヤーに考えさせる、本当に手強いBOT」を完成させる。既存V18準備文書 `docs/V18_READINESS_20261020.md` は破棄しない。強いBOTが実装・検証されたあとでV18へ移る。

公開 `main`／Google Sites埋込は本人の明示リリース承認まで維持。新機能・新マップ・2vs2・記録機能は目的外。まず開発用ブランチで試験する。

## 現状の事実

- `online-game.js` の `botExpertAction(team)` は既に防衛、対空、敵の見える兵士／可視プレイからの資源推定、砦占領、城攻撃、大型資源温存などを扱う。`hard` ではBOT思考間隔が約1.2〜1.9ゲーム秒。反射だけを速くして「強い」と判断しない。
- `tests/online-bot-worker-prototype.js` は現状 **QA専用の非権威提案器**であり、公開BOTの意思決定は担当していない。
- `docs/BOT_WORKER_REAL_DUEL_V12_20261019.md` の12完全試合では、保守的な非同期探索を使えそうな局面はBOT意思決定1,279回中19回（1.49%）。Workerの使える頻度はまだ少ない。
- `docs/BOT_FORT_COUNTER_RESERVE_V13_20261019.md` では砦迎撃のための資源温存が独立160ペアで勝敗改善ゼロ。研究シードの局所的改善を採用根拠にしない。
- `docs/BOT_ATTRITION_FORECAST_V14_20261019.md` では、単体局面では高精度だった消耗予測が実戦での勝勢分類を悪化させた。これも本体へ未採用。
- 既存の`tests/online-bot-evaluation.cjs`、`online-bot-selfplay.cjs`、`online-bot-holdout.cjs`、`online-bot-worker-real-duel.cjs`等の比較資産を再利用する。

## 強化の優先順位

1. **実際の負け方を測る**：同一ルールの旧hard BOTを基準に、赤・青両側／攻勢・防勢・貯蓄・速攻などの異なる相手／新しいseedで比較。単純なスクリプト相手の勝率だけで「強い」とは言わない。
2. **局所戦術の失敗を直す**：砦を守るのか切り捨てるのか、城のHPレース、飛行／大型への適切な迎撃、コスト温存と投入時機。場面別の採用根拠を用意する。
3. **実戦に効いた戦術だけ採用**：すでにQA-onlyとして存在する候補は、合法性・費用・実30Hzでの勝率・両陣営・未知seedでの独立比較に合格したもののみ本体へ昇格。
4. **強さと公平性**：敵の非公開手札や未来行動を読み取らない。本人と同じコスト・回復・射程・ダメージ・配置ルールを使い、隠れた能力補正を禁止。
5. **プレイ可能性**：通常の難易度をいきなり上書きしない。最初はQAだけで試し、十分な改善が確認できたらオフラインの「強敵」難易度を候補にする。ゲストBOTへの適用はiPad WebKit／通信／フレーム時間を検証してから。既存hardの操作感は維持。

## 開発と昇格ゲート

- 最初の改修では**BOT判断ロジックだけ**を変更し、ユニット・建物・スペル・資源・勝利条件を一切変えない。外部APIやモデルの動的ダウンロードを必要としない学校対応の単体ブラウザ設計。
- 事前に「この場面で、旧型より何を良くするのか」「悪化の判定」を固定。研究シードで条件を調整した後、別の未使用seed／他戦術／両陣営で比較する。
- 勝率だけでなく、城HP差、砦保持時間、対空対応率、大型投入、資源遊休、手札空転、戦術の破綻、重い描画の影響を見る。負けを減らしたか、特定の敵だけに特化していないか確認。
- 旧hard vs 候補の同一seed・同一初期山札による対照試合と、旧hard vs 旧hardの陣営差を区別する。新seedの結果に合わせてその場で閾値を再調整しない。
- 新しい判断でメインスレッドが固まるなら採用しない。Worker探索は能力が実証されたときだけ選択する。Worker不可・遅い・画面非表示で旧BOTへ安全に復帰できる必要がある。
- 対象検証：固定seed/holdout、通常30Hz戦闘、100体以上の負荷、Chromium/WebKit、Google Sites sandbox iframe、ゲストBOTのホスト権威検証。実機学校iPadは最後に本人が確認。
- コード変更時は `online-game.js` と `online-ipad.html` / `online-embed.html` の整合を維持。GitHubのテスト結果が最新コミットで成功するまでは `develop` に統合しない。

## 次にやる実作業

1. 既存BOT評価系の最終結果から、`hard` が落とす戦況の再現ケースを抽出する。
2. **1つ目の候補は城攻撃継続 vs 防衛・砦放棄の意思決定**。他の局面に影響しないよう条件を限定し、QA限定で旧BOTとA/B比較する。
3. 十分な効果が出ない場合は棄却し、飛行対策や大型対策など次の失敗要因へ移る。効果を偽装して本体へ入れない。
4. 合格した判断を強敵BOT候補として実装し、テストが通った後に `develop` へ段階的に統合する。
5. 強敵BOTの実プレイを本人が評価できる段階になったらV18の着手を再開する。
