## 核心：AIを再設計するのではなく、既存AIの「対象選択」をデータ化する

**進撃型・占領型・迎撃型の基本AIはこれまで合意した通り維持する。** 行動型の索敵基準・帰還・前進・追撃方向はそのまま。キャラ固有の「何を攻撃するか／何を見つけたら狙うか」だけを共通の0〜3優先度として指定し、個別キャラ向けの条件分岐を増やさずに済ませる。

**基本は3項目のみ**：`castle`（敵城）、`fort`（中立または敵所有の砦）、`unit`（合法な敵キャラ）。

### 優先度の意味（ユーザー発案）
| 優先度 | 攻撃射程内 | 索敵範囲内だが射程外 |
|---:|---|---|
| 0 | 無視 | 無視 |
| 1 | 攻撃候補 | 無視（追わない） |
| 2 | 攻撃候補 | 追跡・接近候補 |
| 3 | 攻撃候補、2より優先 | 追跡・接近候補、2より優先 |

同じ距離帯で複数候補があれば**優先度が高い対象を先に選び、同じ優先度ならより近い対象**。
- **攻撃射程内が常に先**：射程内の1がいるなら、索敵内・射程外の3を追い始めるより1へ攻撃する。
- 攻撃先は攻撃タイミングのたびに再選択（B案）。**移動目標にロックオンを追加しない**。同優先度はその時点で近い方を選ぶ。
- 生存/陣営/対空可否/砦を占領できるか等、攻撃可能性を満たさない対象は対象外。
- 今までの行動型を置き換えない。進撃型は基本的に前進、迎撃型は召喚地点中心の固定索敵円を使い帰還する、占領型は砦への役割を持つ。移動方向の扱いは各行動型のルールを維持。
- 0〜3は**AI内の対象評価部分の設定データ**であり、別の行動型や特別なロック状態の追加を意味しない。

### キャラ設定の典型（確定例と参考例を区別）
| キャラ | 城 | 砦 | 敵キャラ | 備考 |
|---|---:|---:|---:|---|
| 普通の進撃型（典型） | 2 | 0 | 2 | 通常の敵兵・敵城に反応 |
| 基本歩兵（ユーザーが提示した意図） | 2 | **1** | 2 | **砦は射程内だけ攻撃し、索敵内では追わない。個別AI不要** |
| 占領型ライダー（ユーザー提示） | **3** | **3** | **1** | 城と砦は同順位、同時に見えたら近い方を選ぶ。固定ロック不要 |

重装工兵など残りの兵種の数値は、**ここでは確定しない**。前回AI側で提案した「工兵の砦3/城2」「戦車の城3」「迎撃型の城1」は**AIの独断的なアレンジ**なので、採用済みの値として扱わない。

### 特別な対象カテゴリをキャラごとに任意追加
通常は上記3項目だけ。必要なキャラだけ`largeUnit:3`など特別な対象の優先度を追加する。新カテゴリに該当する敵は**固有の値で`unit`値を上書き**し、足し算しない。

```js
// 例：大型キャラだけ特別に優先する兵種
targetPriority: { castle: 2, fort: 0, unit: 2, largeUnit: 3 }
```

- 例：攻城特化なら `{castle:3,fort:0,unit:0}` で他の対象を無視できる。
- 特定敵を0にすることも、`unit:0, flyingUnit:3`で飛行敵のみ狙うことも可能（対空能力を持つことは別途必要）。
- 特殊カテゴリ同士が重なるケース（大型かつ飛行）は、実際に必要なキャラが出た時に競合解決の規則を決める。現在は過剰設計をしない。

## 以前の文書の誤解と撤回
1. **誤：キャラを差別化するために行動型そのものを改造する。** 正：行動型は保ち、対象の優先度だけを数値化する。
2. **誤：砦を追わない歩兵は「砦2＋AIで砦への移動禁止」の特例が必要。** 正：`fort:1`でそのまま表現できる。
3. **誤：ライダーが砦を選んだら移動ロックオンを保持。** 正：特別なロックなし。城3と砦3は同順位ならその時点の最寄り。
4. **誤：ライダー城2・砦2、または工兵だけ城2・砦3を自動採用。** 正：ユーザーの提示はライダー城3・砦3・敵1。ほかの数値は既存の役割から別途検討する。
5. **誤：迎撃型の城優先度を変更して行動型の守備ルールを上書き。** 正：迎撃型の固定索敵・帰還ルールは独立して保持。
6. **誤：優先度を導入する目的は3行動型の全面的な再設計。** 正：対象選択を共通関数とデータで表現し、今までのAIを単純に保つため。

## 実装時に分離すべきこと
- 従来の `nearbyEnemy()` 等にハードコードされている、大型加点、密集加点、城加点、以前の対象維持補正を優先度式へ移行した場合の差分を確認する。
- `CLASSES` へ各キャラの `targetPriority` を追加する方式が適切。既存8軸と併存するデータ欄であり、既存性能値を無断変更しない。
- 行動型（normal/capture/guard）の前進・砦へ移動・固定索敵円・帰還の責務は残す。**何を狙うかだけ数値化し、複雑な新状態やロック処理を増やさない。**
- 例外が必要な時も、まず「優先度0/1/2/3の値で表現できないか」を考える。値で表現できるならコードの追加分岐を作らない。
